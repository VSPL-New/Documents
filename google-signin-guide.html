US-101 · Google Sign-In

How to Test and Configure Google Sign-In

Complete guide for local development with the mock adapter and production deployment with real Google OAuth tokens. Covers backend configuration, PowerShell examples, and Google Cloud Console setup.

Overview

The backend supports Google Sign-In via a port/adapter pattern. A mock adapter handles development and CI — no Google account or internet needed. The HTTP adapter runs in production, validating tokens against Google's tokeninfo endpoint.

Registration flow — new Google user
POST /social/google
→
validate token
→
socialSessionToken returned
POST /social/google/initiate-mobile
→
mobile OTP sent
POST /social/google/verify-mobile
→
JWT issued · IDENTITY_VERIFICATION_PENDING
Login flow — returning Google user
POST /social/google
→
token validated
→
JWT issued immediately

Mock vs HTTP mode

Dev / Mock
  • No Google Cloud setup needed
  • No real ID tokens required
  • Token format: mock-<suffix>
  • Token invalid always fails
  • OTPs printed to application log
  • Works fully offline
Prod / HTTP
  • Calls Google's tokeninfo endpoint
  • Validates token signature and expiry
  • Checks aud against configured client IDs
  • Requires valid Google Cloud project
  • Supports Web, Android, iOS tokens
  • Rejects any token not issued for ValueX

The active mode is controlled by a single environment variable. All other behaviour is identical between modes.

Dev configuration Mock mode

The mock adapter is active by default — nothing in application.yml needs to change for local dev. Confirm the effective values in your .env or leave them unset:

.env (or defaults)
# Mock adapter — no real Google credentials needed
GOOGLE_OAUTH_PROVIDER=mock

# These are ignored in mock mode — can be left blank
GOOGLE_CLIENT_ID_WEB=
GOOGLE_CLIENT_ID_ANDROID=
GOOGLE_CLIENT_ID_IOS=

Mock token format

Send any string starting with mock- as the idToken. The suffix becomes the user identity — use different suffixes to simulate different Google accounts. The special token invalid always throws ERROR_INVALID_GOOGLE_TOKEN.

Token examples
mock-alice   →  sub=google-sub-alice,  email=alice@gmail.com
mock-bob     →  sub=google-sub-bob,    email=bob@gmail.com
mock-user1   →  sub=google-sub-user1,  email=user1@gmail.com
invalid      →  throws ERROR_INVALID_GOOGLE_TOKEN
💡
The OTP sent during initiate-mobile is printed to the Spring Boot log. Search for "OTP sent" or "[DEV-MOCK]".

Dev test: New Google user Mock

Complete 3-step flow for a Google account that has never signed into ValueX before.

Step 1 — Validate Google token

powershell
Invoke-RestMethod -Method Post `
  -Uri "http://localhost:8080/api/v1/auth/social/google" `
  -ContentType "application/json" `
  -Body '{"idToken": "mock-alice"}' | ConvertTo-Json -Depth 5

Expected response — requiresMobileVerification: true:

json · response
{
  "success": true,
  "data": {
    "requiresMobileVerification": true,
    "socialSessionToken": "3f8a1c2d-...",
    "googleEmail": "alice@gmail.com"
  }
}

Step 2 — Send mobile OTP

Use the socialSessionToken from step 1.

powershell
Invoke-RestMethod -Method Post `
  -Uri "http://localhost:8080/api/v1/auth/social/google/initiate-mobile" `
  -ContentType "application/json" `
  -Body '{
    "socialSessionToken": "3f8a1c2d-...",
    "mobile": "9876543210",
    "termsAccepted": true,
    "consentGiven": true
  }' | ConvertTo-Json -Depth 5

Check the application log for the OTP:

log output
[DEV-MOCK] Sending OTP 483920 to mobile=9876543210 purpose=MOBILE_VERIFY

Step 3 — Verify OTP and get JWT

powershell
Invoke-RestMethod -Method Post `
  -Uri "http://localhost:8080/api/v1/auth/social/google/verify-mobile" `
  -ContentType "application/json" `
  -Body '{
    "socialSessionToken": "3f8a1c2d-...",
    "mobile": "9876543210",
    "otp": "483920"
  }' | ConvertTo-Json -Depth 5
json · response
{
  "success": true,
  "data": {
    "accessToken": "eyJhbGci...",
    "refreshToken": "eyJhbGci...",
    "aadhaarVerified": false,
    "userId": "a1b2c3d4-..."
  }
}

The account is now in IDENTITY_VERIFICATION_PENDING state. The user can proceed to Aadhaar verification or skip it.

Dev test: Returning Google user Mock

Once a Google account has been linked (via flow 1), subsequent sign-ins return a JWT in a single call — no mobile step needed.

powershell
Invoke-RestMethod -Method Post `
  -Uri "http://localhost:8080/api/v1/auth/social/google" `
  -ContentType "application/json" `
  -Body '{"idToken": "mock-alice"}' | ConvertTo-Json -Depth 5
json · response
{
  "success": true,
  "data": {
    "requiresMobileVerification": false,
    "accessToken": "eyJhbGci...",
    "refreshToken": "eyJhbGci...",
    "aadhaarVerified": false,
    "userId": "a1b2c3d4-..."
  }
}
💡
The same mock-alice token will always resolve to the same google-sub-alice identity. Re-running flow 1 with a different suffix (mock-bob) creates a separate user.

Dev test: Link Google to existing mobile account Mock

A user already registered via mobile OTP (US-001) can link their Google account for future convenience login. Their mobile must be in ACTIVE state.

Step 1 — initiate with a new Google token (not yet linked)

powershell
Invoke-RestMethod -Method Post `
  -Uri "http://localhost:8080/api/v1/auth/social/google" `
  -ContentType "application/json" `
  -Body '{"idToken": "mock-charlie"}' | ConvertTo-Json -Depth 5
# → requiresMobileVerification: true, socialSessionToken: "xyz..."

Step 2 — use the mobile of the existing ACTIVE account

powershell
Invoke-RestMethod -Method Post `
  -Uri "http://localhost:8080/api/v1/auth/social/google/initiate-mobile" `
  -ContentType "application/json" `
  -Body '{
    "socialSessionToken": "xyz...",
    "mobile": "9999999999",
    "termsAccepted": true,
    "consentGiven": true
  }' | ConvertTo-Json -Depth 5

Step 3 — verify OTP

After verification, Google is linked to the existing account. The session token is deleted from Redis. No state transition occurs — the account stays ACTIVE.

⚠️
Account must be ACTIVE. If the mobile account is still in EMAIL_VERIFICATION_PENDING or IDENTITY_VERIFICATION_PENDING, the system returns ERROR_INVALID_STATE. The user must complete their existing registration first.

Google Cloud Console setup Prod

Only needed once. The person with access to the Google Cloud project should complete these steps before switching to HTTP mode.

  1. Create or select a Google Cloud project
    Go to console.cloud.google.com. Create a project named "ValueX" (or use an existing one). Note the project ID.
  2. Configure the OAuth Consent Screen
    Navigate to APIs & Services → OAuth consent screen. Set user type to External. Fill in: App name ("ValueX"), support email, developer contact email. Add scopes: openid, email, profile — nothing else. Add test users while in Testing mode.
  3. Collect SHA-1 fingerprints for Android
    The Android client ID requires the keystore SHA-1. Run both commands and keep the output ready:
powershell · debug keystore
keytool -list -v `
  -keystore "$env:USERPROFILE\.android\debug.keystore" `
  -alias androiddebugkey `
  -storepass android -keypass android
powershell · release keystore
keytool -list -v `
  -keystore "C:\path\to\release.keystore" `
  -alias your-alias-name
💡
If using Play App Signing (recommended), get the SHA-1 from Play Console → Your App → Setup → App Signing → App signing key certificate. This is the fingerprint that must be registered — not the upload key.

Create OAuth client IDs Prod

Go to APIs & Services → Credentials → Create Credentials → OAuth client ID. Create three separate client IDs:

  1. Web application client ID
    Application type: Web application. Name: "ValueX Web". No redirect URIs needed — this client ID is used only for backend token validation. Copy the client ID; it goes into GOOGLE_CLIENT_ID_WEB.
  2. Android client ID
    Application type: Android. Package name: com.valuex.app. SHA-1: paste the fingerprint from the keytool step. Create one entry for debug SHA-1, a second for release SHA-1. Download google-services.json and place it at android/app/google-services.json in the Flutter project.
  3. iOS client ID
    Application type: iOS. Bundle ID: com.valuex.app. Download GoogleService-Info.plist and place it at ios/Runner/GoogleService-Info.plist. Copy the REVERSED_CLIENT_ID value from the plist — it is required as a URL scheme in Info.plist.
xml · ios/Runner/Info.plist — add URL scheme
<key>CFBundleURLTypes</key>
<array>
  <dict>
    <key>CFBundleURLSchemes</key>
    <array>
      <string>com.googleusercontent.apps.YOUR_REVERSED_CLIENT_ID</string>
    </array>
  </dict>
</array>

Production configuration HTTP mode

Set the following environment variables in your production deployment (Docker Compose, Kubernetes secret, or hosting platform config):

Environment variable Value Notes
GOOGLE_OAUTH_PROVIDER http Activates real token validation. Default is mock.
GOOGLE_CLIENT_ID_WEB xxx.apps.googleusercontent.com Web application client ID from Google Cloud Console
GOOGLE_CLIENT_ID_ANDROID xxx.apps.googleusercontent.com Android client ID. Tokens from the Flutter Android app will carry this as aud.
GOOGLE_CLIENT_ID_IOS xxx.apps.googleusercontent.com iOS client ID. Tokens from the Flutter iOS app will carry this as aud.

Add these to .env.example so other developers know they exist:

.env.example
# Google OAuth — set all three client IDs in production
# Leave provider=mock for local dev (default)
GOOGLE_OAUTH_PROVIDER=mock
GOOGLE_CLIENT_ID_WEB=
GOOGLE_CLIENT_ID_ANDROID=
GOOGLE_CLIENT_ID_IOS=
⚠️
All three client IDs must be set when using HTTP mode. The backend validates the aud claim in every Google token against all three. Leaving one blank means tokens from that platform will be rejected.

Verify the switch is active

log output
# In application logs at startup, look for:
INFO  c.v.a.a.o.HttpGoogleTokenAdapter - Initialized with 3 accepted client IDs

# If you see MockGoogleTokenAdapter instead, check GOOGLE_OAUTH_PROVIDER

Getting a real Google ID token for prod testing

With HTTP mode active, you need a real Google ID token to test the endpoints. Two options:

Option A — Google OAuth Playground

  1. Open OAuth Playground
    Go to developers.google.com/oauthplayground
  2. Configure with your web client ID
    Click the gear icon (top right) → check "Use your own OAuth credentials" → enter your Web Client ID and Client Secret.
  3. Authorize the openid scope
    In Step 1, type openid email profile in the input and click Authorize. Sign in with a Google account.
  4. Exchange for tokens
    Click Exchange authorization code for tokens. The response contains id_token — copy it.
  5. Use the token in your API call
    Replace PASTE_ID_TOKEN_HERE in the PowerShell example below. Tokens expire in 1 hour.
powershell · test with real token
Invoke-RestMethod -Method Post `
  -Uri "https://your-api.valuex.in/api/v1/auth/social/google" `
  -ContentType "application/json" `
  -Body '{"idToken": "PASTE_ID_TOKEN_HERE"}' | ConvertTo-Json -Depth 5

Option B — Flutter app in debug mode

Run the Flutter app with the debug Google client ID. After GoogleSignIn().signIn(), print authentication.idToken to the debug console and use it directly in PowerShell for API-level testing.

🔒
Never share or commit real ID tokens. They contain user PII (email, name) and are valid for up to 1 hour. Treat them like passwords.

API endpoint reference

All three endpoints are public — no JWT required. Base path: /api/v1/auth

MethodPathAuthPurpose
POST/social/googleNoneValidate Google ID token. Returns JWT if linked, or socialSessionToken if new user.
POST/social/google/initiate-mobileNoneSend mobile OTP to link a mobile number to the new Google account. Requires socialSessionToken.
POST/social/google/verify-mobileNoneVerify OTP, create or link account, return JWT. Session token deleted after use.

Session token behaviour

ℹ️
The socialSessionToken is a UUID stored in Redis with a 10-minute TTL. It is deleted after successful OTP verification. If the user waits more than 10 minutes between steps, they must restart from /social/google.

Error reference

ERROR_INVALID_GOOGLE_TOKEN
Token validation failed In mock mode: only triggered by passing the string invalid. In HTTP mode: token is expired, signature invalid, or aud does not match any configured client ID.
ERROR_SOCIAL_SESSION_EXPIRED
Redis session missing More than 10 minutes elapsed between steps, or the session token was already consumed. Ask the user to sign in with Google again.
ERROR_SOCIAL_SESSION_INVALID
Incomplete session initiate-mobile was not called before verify-mobile. The session in Redis has only 3 parts (no mobile appended yet).
ERROR_SOCIAL_ACCOUNT_ALREADY_LINKED
Duplicate Google link The mobile number provided belongs to an account that already has a Google account linked. Each Google account can be linked to one ValueX account only.
ERROR_INVALID_STATE
Incomplete existing registration The mobile number already exists in the database but the account is not ACTIVE (e.g. stuck at EMAIL_VERIFICATION_PENDING). The user must complete their original registration first.
ERROR_MOBILE_MISMATCH
Mobile changed between steps The mobile passed to verify-mobile does not match what was stored in Redis during initiate-mobile. The client must send the same mobile in both calls.
ERROR_INVALID_OTP
Wrong OTP Standard OTP validation failure. Check the mock adapter log for the correct 6-digit code in dev.
ERROR_OTP_EXPIRED
OTP TTL elapsed The 5-minute OTP window has passed. Call initiate-mobile again to resend.
ERROR_OTP_RATE_LIMIT
Too many OTP requests More than 3 send attempts per mobile per 10-minute window. Wait for the window to reset.
ERROR_TERMS_NOT_ACCEPTED
Missing consent termsAccepted or consentGiven was false in the initiate-mobile request.

Go-live checklist

Complete all items before switching GOOGLE_OAUTH_PROVIDER to http in production.

Google Cloud Console

  • OAuth consent screen configured with app name, support email, and privacy policy URL
  • Consent screen submitted for Google verification (required before external users can sign in)
  • Web application client ID created
  • Android client ID created with debug SHA-1 and release SHA-1
  • iOS client ID created with correct Bundle ID

Flutter project

  • google-services.json placed at android/app/
  • GoogleService-Info.plist placed at ios/Runner/
  • REVERSED_CLIENT_ID URL scheme added to ios/Runner/Info.plist
  • Google Sign-In plugin configured in android/build.gradle
  • google_sign_in package in pubspec.yaml

Backend

  • GOOGLE_OAUTH_PROVIDER=http set in production environment
  • GOOGLE_CLIENT_ID_WEB set to the web client ID
  • GOOGLE_CLIENT_ID_ANDROID set to the Android client ID
  • GOOGLE_CLIENT_ID_IOS set to the iOS client ID
  • End-to-end test with a real Google token (via OAuth Playground) passing
  • .env.example updated with the four new variable names

Legal

  • Privacy policy live at a public URL, mentioning Google Sign-In data usage
  • Privacy policy URL registered in the Google OAuth consent screen
