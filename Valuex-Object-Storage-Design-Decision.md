# ValueX Storage Design Decision

**Document Type:** Architecture Decision / Implementation Design Input\
**Status:** Approved for implementation planning\
**Product:** ValueX\
**Decision Scope:** Image and media object storage\
**Primary Backend:** Java Spring Boot\
**AI Services:** Python\
**Mobile:** Flutter\
**Web:** React\
**Date:** 2026-08-31

------------------------------------------------------------------------

## 1. Purpose

This document defines the storage architecture decision for images and
media uploaded or generated by ValueX. It is intended as direct input
to architecture/design and implementation agents updating the HLD/LLD,
infrastructure, backend storage abstraction, media processing, security,
observability, and tests.

ValueX is an image-centric marketplace whose core experience is:
**click a photo to sell; click a photo to buy.**

The platform therefore requires storage optimized for total cost, high
read volumes, CDN delivery, secure evidence storage, lifecycle
management, and future portability.

## 2. Decision Summary

Use **Cloudflare R2 Standard + Cloudflare CDN** for active marketplace
images during MVP and early growth.

All object-storage access must go through a **vendor-neutral
S3-compatible abstraction** in Spring Boot.

Use private storage and short-lived signed access for transaction,
return, support, and dispute evidence. Generate optimized image variants
for application delivery; do not routinely serve original phone-camera
images.

When active image storage reaches approximately **10--20 TB**, benchmark
**Backblaze B2 + Cloudflare CDN** against R2 using real production
measurements.

  Decision                          Choice
  --------------------------------- ------------------------------------
  Active image object store         Cloudflare R2 Standard
  Delivery                          Cloudflare CDN
  Storage API                       S3-compatible abstraction
  Active listing delivery           CDN-backed controlled delivery
  Sensitive evidence                Private + short-lived signed URLs
  Preferred delivery format         AVIF
  Fallback                          WebP, then JPEG where required
  Original camera image             Private; retained only as required
  Future alternative                Backblaze B2 + Cloudflare CDN
  Provider calls from domain code   Prohibited

## 3. Workload and Design Drivers

Media is created for seller listings, AI listing analysis, buyer photo
search, seller pre-shipment proof, buyer delivery proof, returns,
disputes, profiles, support attachments, and fraud/moderation workflows.

Listing images are read much more frequently than written because they
appear in home feeds, search results, saved items, listing details,
profiles, carts, and order history. Therefore egress, CDN cache
behavior, and request charges matter alongside raw \$/GB.

## 4. Architecture Principles

1.  **PostgreSQL is the metadata source of truth.** Object storage
    contains binaries.
2.  **No permanent storage credentials in Flutter or React.**
3.  **Large uploads should not unnecessarily transit Spring Boot.**
    Prefer controlled direct uploads using short-lived presigned URLs.
4.  **Stored does not mean public.** Media access is policy-controlled.
5.  **Optimize once, deliver many times.**
6.  **Provider choice is infrastructure detail.** Domain code depends on
    interfaces.
7.  **Sensitive evidence is private and isolated.**
8.  **Deletion is lifecycle-controlled.** Listing deletion must not
    destroy evidence required by an order, return, dispute, fraud
    investigation, or retention rule.

## 5. Logical Storage Classes

### 5.1 Active listing media

Includes listing photos, derivatives, and appropriate profile media.

-   Storage: R2 Standard
-   Delivery: Cloudflare CDN
-   Characteristics: high-read, latency-sensitive

### 5.2 Transaction evidence

Includes seller packaging/item-condition photos and buyer
package/received-item photos.

-   Storage: private R2
-   Delivery: no unrestricted public URL
-   Access: authorization + short-lived signed URL

### 5.3 Return/dispute evidence

Includes return condition, dispute, moderation, and transaction-support
evidence.

-   Storage: private
-   Access: role/relationship/state authorization + signed URL
-   Retention: policy-driven

### 5.4 Photo-search input

Buyer search photos are temporary processing inputs, not ordinary
listing assets. Implement configurable short-lived retention and
automatic cleanup unless the final product/privacy policy requires
otherwise.

### 5.5 Archived media

Rarely accessed retained objects may later use an archival/infrequent
tier after retrieval cost, minimum duration, and access patterns are
validated.

## 6. Bucket / Namespace Design

Environment isolation is mandatory.

``` text
valuex-{env}-listing-media
valuex-{env}-evidence
valuex-{env}-profile-media
valuex-{env}-search-input
valuex-{env}-support-media

{env} = dev | staging | prod
```

Example object keys:

``` text
listings/{listingId}/{mediaId}/original.jpg
listings/{listingId}/{mediaId}/thumb.avif
listings/{listingId}/{mediaId}/card.avif
listings/{listingId}/{mediaId}/detail.webp
listings/{listingId}/{mediaId}/zoom.webp
evidence/orders/{orderId}/{evidenceId}/original.jpg
evidence/disputes/{disputeId}/{evidenceId}/original.jpg
profiles/{userId}/{mediaId}/profile.webp
search/{requestId}/input.jpg
```

Use opaque IDs. Never put Aadhaar, mobile number, email, bank details,
or other PII in object keys.

## 7. Image Variant Strategy

Initial target envelopes must be performance-tested:

  Variant     Use                          Approx. dimension         Target payload
  ----------- -------------------------- ------------------- ----------------------
  Thumbnail   compact grid/search                200--300 px              20--50 KB
  Card        feed/listing card                  500--600 px             60--120 KB
  Detail      listing detail                   1000--1200 px            150--300 KB
  Zoom        enlarged view                        \~1600 px            300--600 KB
  Original    evidence/AI/reprocessing                source   not routine delivery

Preferred format negotiation:

``` text
AVIF -> WebP -> JPEG
```

Correct orientation and strip unnecessary metadata from public
derivatives. EXIF geolocation must not be exposed unintentionally.

## 8. Upload Architecture

``` text
Flutter / React
  -> request upload authorization
Spring Boot
  -> authenticate/authorize
  -> validate owner, lifecycle state, quota
  -> create MediaAsset=PENDING_UPLOAD
  -> issue short-lived upload URL
Client
  -> direct upload
R2
  -> completion/event
Media Worker
  -> verify actual file
  -> security scan
  -> normalize orientation
  -> strip unsafe metadata
  -> generate derivatives
  -> checksum/perceptual hash
  -> store derivatives
PostgreSQL
  -> MediaAsset=READY
```

Required validation:

-   authenticated actor;
-   resource ownership;
-   lifecycle-state eligibility;
-   image-count and size limits;
-   magic bytes/decoded type, not filename alone;
-   dimensions and decompression-bomb limits;
-   corruption detection;
-   malware/security checks where applicable.

Suggested upload states:

``` text
PENDING_UPLOAD
UPLOADED
VALIDATING
PROCESSING
READY
REJECTED
QUARANTINED
DELETION_PENDING
DELETED
```

## 9. Media Processing

Processing is asynchronous.

``` text
UploadCompleted
 -> MediaProcessingRequested
 -> Worker
    - verification
    - EXIF sanitization
    - normalization
    - AVIF/WebP variants
    - checksum/perceptual hash
    - optional AI preprocessing
 -> MediaProcessingCompleted
```

Use bounded retries and failed/dead-letter handling. Never mark an asset
READY when mandatory derivatives failed.

## 10. Delivery Architecture

Active media:

``` text
Flutter / React
       |
Cloudflare CDN
       |
   cache hit -> response
       |
   cache miss
       v
Cloudflare R2
```

Prefer versioned/immutable derivative keys so aggressive caching is
safe.

Private evidence:

``` text
Client/Admin
 -> authenticated Spring Boot request
 -> authorization (actor + role + transaction relationship + state)
 -> short-lived signed URL
 -> private object
```

Do not persist signed URLs as canonical database values. Persist object
references.

## 13. Security Requirements

Mandatory:

-   TLS in transit and encryption at rest;
-   least-privilege credentials;
-   separate environment credentials;
-   approved secret manager;
-   short-lived upload/download authorization;
-   no PII in keys;
-   private-by-default evidence;
-   authorization before evidence access;
-   upload content validation;
-   audit sensitive evidence access;
-   lifecycle-controlled deletion;
-   no storage credentials in clients.

Never log signed-URL secrets, access tokens, provider secrets, or raw
sensitive evidence.

## 14. Retention and Deletion

Retention is configurable by purpose. Final durations must be reconciled
with the latest PRD, privacy requirements, dispute/fraud policies, and
legal/compliance review.

At minimum configure:

``` text
ACTIVE_LISTING_MEDIA
SOLD_LISTING_MEDIA
TRANSACTION_EVIDENCE
DISPUTE_EVIDENCE
RETURN_EVIDENCE
PHOTO_SEARCH_INPUT
PROFILE_MEDIA
SUPPORT_ATTACHMENT
```

Safe deletion:

``` text
Deletion Requested
 -> reference/hold checks
    - active order?
    - return?
    - dispute?
    - investigation?
    - retention/legal hold?
 -> DELETION_PENDING
 -> delete variants
 -> delete original when allowed
 -> DELETED
```

## 15. Recovery and Reconciliation

Design must cover accidental deletion protection, metadata recovery,
versioning where justified, and any DR replication required by the final
DR design.

Run reconciliation jobs to detect:

``` text
DB metadata exists but object missing
object exists but DB metadata missing
READY asset missing mandatory derivative
expired temporary object not deleted
```

## 16. Observability

Track:

**Capacity** - stored bytes/object count; - storage by media purpose; -
growth/day; - derivative/original ratio.

**Traffic** - CDN requests; - cache-hit ratio; - cache misses; - R2
Class A/B operations; - bytes delivered; - signed evidence downloads.

**Processing** - upload success; - processing latency/success; - queue
depth; - retries; - quarantines; - derivative failures.

**Cost** - GB-month; - operations; - transformations; -
backup/replication.

**Security** - unusual signed-URL creation; - mass evidence access; -
abnormal uploads; - rejected uploads; - authorization failures.

## 17. Cost Controls

Mandatory controls:

1.  optimize images;
2.  CDN-cache public derivatives;
3.  never use originals for feeds/search cards;
4.  remove abandoned uploads;
5.  expire photo-search inputs;
6.  monitor cache hit ratio;
7.  enforce file/image-count limits;
8.  lifecycle archived content;
9.  maintain storage cost dashboards.

Capacity reference:

``` text
1M images x 500 KB   ~= 500 GB
10M images x 500 KB  ~= 5 TB
100M images x 500 KB ~= 50 TB
```

Use measured production object sizes and access frequency for
forecasting.

## 18. Provider Decision

### Cloudflare R2 Standard selected because

-   image-heavy/high-read marketplace workload;
-   CDN-oriented delivery;
-   S3-compatible interface;
-   attractive egress model;
-   no need to impose long retention constraints on hot listing images;
-   operational simplicity for MVP.

Do not hardcode provider pricing in application logic or architecture
assumptions.

### R2 Infrequent Access

Do not use for active listing images. Evaluate only for specific
low-access retained data after reviewing retrieval cost, minimum
duration, and access patterns.

### Backblaze B2 review trigger

Perform a cost/architecture review when:

-   active storage exceeds \~10 TB;
-   20 TB is forecast within six months;
-   R2 cost becomes material;
-   production cache-hit ratio is stable.

Compare **total cost**, including storage, requests, egress/delivery,
operations, support, backup, migration, and engineering overhead.

## 19. Portability Requirements

-   domain entities reference media IDs, not provider URLs;
-   bucket/key details stay in media infrastructure;
-   use S3-compatible interfaces where practical;
-   do not expose R2-specific identifiers as business identifiers;
-   never persist signed URLs;
-   externalize provider config;
-   provide migration/reconciliation tooling.

Provider migration should primarily affect infrastructure, storage
adapter, and migration tooling---not listing/order/dispute/mobile/web
business logic.

## 20. Infrastructure-as-Code Requirements

The infrastructure repo must manage, where supported:

-   buckets;
-   environment isolation;
-   access policies;
-   CORS;
-   lifecycle policies;
-   custom delivery domain;
-   secret references;
-   monitoring/alerts;
-   CDN/cache configuration.

Manual production configuration must not be the long-term source of
truth.

## 23. Failure Handling

-   R2 unavailable: fail gracefully and retry async work; never mark
    READY.
-   Worker failure: bounded retries then explicit failed/rejected state.
-   CDN issue: controlled fallback only where appropriate; never bypass
    private-media authorization.
-   Orphan upload: detect and delete after configured grace period.
-   Mandatory listing media not READY: listing cannot progress to states
    requiring completed media.

-   [ ] No permanent R2 credentials in clients.

-   [ ] Short-lived direct upload authorization works.
-   [ ] Uploaded content is independently validated.
-   [ ] AVIF/WebP variants generated.
-   [ ] Appropriate variants used by feed/search/detail.
-   [ ] Original images not routinely served.
-   [ ] Public derivatives CDN cached.
-   [ ] Evidence private and authorization protected.
-   [ ] Evidence access uses short-lived signed URLs.
-   [ ] No PII in object keys.
-   [ ] Media metadata stored in PostgreSQL.
-   [ ] Media lifecycle states implemented.
-   [ ] Abandoned uploads automatically removed.
-   [ ] Retention configurable by purpose.
-   [ ] Deletion respects transaction/dispute/investigation holds.

-   [ ] Integration/security/performance tests pass.

## 30. Final Decision

**Use Cloudflare R2 Standard as the initial ValueX image/object
storage platform, fronted by Cloudflare CDN for active marketplace image
delivery.**

Use a **vendor-neutral S3-compatible storage abstraction**, mandatory
image optimization, private evidence storage, signed access,
lifecycle-controlled retention/deletion, and strong observability.

Optimize for **total marketplace media cost**, not storage \$/TB alone.

Re-evaluate **Backblaze B2 + Cloudflare CDN** at approximately **10--20
TB of active storage** using real production workload measurements.
